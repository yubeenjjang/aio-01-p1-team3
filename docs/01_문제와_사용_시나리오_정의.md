## 1. 프로젝트 개요

### 프로젝트 주제

스터디 관리 웹 서비스

### 현재 구현 기준

현재 구현은 간소화 MVP 범위를 기준으로 합니다. 상세 데이터베이스 설계와 확장 API는 핵심 기능이 안정된 뒤 적용하는 목표 설계입니다.

## 2. 문제 정의

학습과 스터디 활동에 필요한 기록·모집·분석 기능이 여러 서비스에 분산되어 있어, 사용자가 학습 현황을 파악하고 스터디를 지속적으로 운영하기 어렵습니다.

1. **학습 기록의 분산**  
   메모 앱, 카카오톡, 디스코드 등에 학습 기록이 흩어져 누적 학습량과 목표 달성 현황을 확인하기 어렵습니다.

2. **스터디 모집과 참여의 어려움**  
   관심 분야, 활동 시간대와 목표가 비슷한 스터디원이나 그룹을 찾기 어렵습니다.

3. **소통 및 운영 관리의 불편함**  
   공지와 할 일이 채팅에 묻히고 출석·인증·참여 현황을 수작업으로 관리해야 합니다.

4. **학습 동기와 스터디 유지의 어려움**  
   목표와 성취도가 명확하게 보이지 않아 개인의 학습 의지와 그룹 참여가 지속되기 어렵습니다.

5. **학습 분석과 피드백의 부족**  
   누적된 기록을 학습 습관과 부족한 영역, 다음 학습 방향에 관한 피드백으로 활용하기 어렵습니다.

## 3. 애자일 개발 범위

애자일 방식으로 개발하며, 초기 버전에서는 문제 1·2·5를 우선 구현합니다.

| 우선순위 | 문제 | 초기 구현 범위 |
| --- | --- | --- |
| 1 | 학습 기록의 분산 | 학습 기록 등록·수정·삭제, 공부 시간·과목 관리, 인증 사진 등록, 누적 학습량 확인 |
| 2 | 스터디 모집과 참여의 어려움 | 스터디 생성·검색·조회·참여·탈퇴, 모집 상태와 참여 인원 확인 |
| 3 | 학습 분석과 피드백 부족 | 통계 조회, AI 분석 요청·성공·실패 처리, 과목별 학습 현황·부족한 영역·다음 학습 목표 추천 |

| 후속 범위 | 예정 기능 |
| --- | --- |

## 5. 사용 시나리오

### 개인 학습 기록

사용자는 과목, 공부 시간, 학습 내용을 한곳에 기록합니다. 대시보드에서 누적 학습량과 과목별 공부 시간을 확인하며, 기록이 없으면 학습 기록 등록 안내를 확인합니다.

### 스터디 검색·모집·참여

사용자는 관심 분야, 목표, 활동 시간대를 기준으로 스터디를 검색하거나 직접 모집합니다. 원하는 결과가 없으면 새로운 스터디를 생성하며, 권한이 없는 스터디에는 접근할 수 없습니다.

### AI 학습 분석

사용자는 누적된 학습 기록을 바탕으로 AI 분석을 요청합니다. 과목별 학습 현황, 부족한 영역과 다음 학습 목표를 추천받으며, API 오류가 발생하면 오류 안내를 확인하고 다시 요청합니다.

### 관리자: 학습 기록 현황과 오류 분석

관리자는 학습 기록의 등록·수정·삭제 건수와 과목별 이용 현황을 확인합니다. 오류가 증가하면 실패 로그를 필터링해 발생 시간, 사용자와 오류 내용을 조회합니다.

### 관리자: 스터디 운영 현황

관리자는 스터디 생성·검색·참여 건수와 모집 중인 스터디 현황을 확인합니다. 검색 결과가 없거나 참여가 낮은 분야를 파악해 모집 조건과 검색 기능을 개선합니다.

### 관리자: AI 분석 품질 관리

관리자는 AI 분석 요청량, 성공률, 오류율과 평균 응답 시간을 확인합니다. 오류가 발생하면 AI 실패 로그를 조회합니다. 사용자 평가를 활용한 분석 품질 개선은 팀 합의가 필요한 후보 기능입니다.

## 6. 예외 상황 및 화면 처리

| 상황 | 화면 처리 |
| --- | --- |
| 정상 | 학습 기록, 스터디 정보, 통계와 AI 분석 결과를 표시합니다. |
| 빈 데이터 | 학습 기록이나 검색 결과가 없음을 안내하고 등록·검색 버튼을 제공합니다. |
| 권한 오류 | 본인의 기록이나 참여한 스터디만 접근할 수 있도록 제한합니다. |
| API 오류 | 데이터를 불러오지 못했다는 안내와 재시도 버튼을 표시합니다. |

### 공통 처리 원칙

대시보드 데이터가 없으면 데이터 없음을, 관리자 권한이 없으면 접근 권한 없음을, API 호출이 실패하면 조회 실패와 재시도 버튼을 표시합니다.

## 8. 개선 후보｜팀 합의 필요

> 아래 항목은 현재 확정된 요구사항이 아닙니다. 다음 회의에서 우선순위·구현 범위·측정 기준을 팀이 합의한 뒤 반영 여부를 결정합니다.

### 후보 1. 기능별 성공 기준 설정

구현과 테스트의 완료 여부를 판단할 수 있도록 다음과 같은 측정 지표를 정의하는 방안을 검토합니다.

| 영역 | 측정 지표 예시 |
| --- | --- |
| 학습 기록 | 일주일 학습 기록 작성률, 사용자별 누적 학습 시간 |
| 스터디 모집 | 검색 횟수, 스터디 생성 수, 검색 후 참여 전환율 |
| AI 학습 분석 | 분석 요청 수, 성공률, 평균 응답 시간, 오류율 |
| 서비스 안정성 | API 오류율, 재시도 성공률 |

### 후보 2. 공통 로그 데이터 정의

모든 주요 기능의 로그에 `timestamp`, `user_id`, `study_id`, `action`, `status`, `error_code`, `latency_ms`를 공통으로 기록하는 방안을 검토합니다. 인증 사진이나 학습 내용처럼 민감할 수 있는 원문 데이터는 로그에 직접 저장하지 않고, 필요한 식별자와 처리 결과만 기록하는 원칙도 함께 논의합니다.

### 후보 3. AI 분석 결과 평가 수집

AI 분석 결과를 받은 사용자가 만족도 점수(예: 1~5점)와 의견을 등록하는 기능을 검토합니다. 도입 시 관리자는 이 평가 데이터와 AI 요청 성공·실패 로그를 함께 확인해 분석 품질 개선 항목을 도출합니다.

| 우선 기능 | 완료 조건 예시 |
